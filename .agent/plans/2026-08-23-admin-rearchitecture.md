# 后台页面化重构与外部图床媒体中心

> 状态：数据模型与媒体基础能力已实现；后台结构性重构验收失败，待重新实现
>
> 建立日期：2026-08-23
>
> 实施约束：已发布能力和待重做范围以“进度”“验证命令与结果”“未完成项”明确区分；不得因为部分代码已上线而把后台结构重构标记为完成。

## 目的与用户可见结果

重构 `/admin/` 的内容组织、字段和发布入口，使非技术维护者按照前台页面完成维护，而不必理解底层 Markdown/YAML 文件如何拆分。重构完成后：

- 首页公告、四个活动展示位、三项荣誉及首页文案在“首页管理”语境内维护；
- 活动编辑只描述活动自身，首页选取逻辑全部移至首页设置；
- 活动中心保留独立、含义明确的置顶能力；
- 后台只显示一个“待发布”暂存入口，每条内容仍使用 Decap 原生的独立暂存和独立发布，不引入发布批次；
- 仓库媒体上传被自定义外部图床媒体中心替代；维护者可在本机配置通用 HTTP 图床、上传并选图，也可直接粘贴完整图片 URL；
- Decap 原生“媒体”与自定义“图片中心”合并；最终后台只保留一个名为“图片中心”的入口、一套图片索引和一套选图/上传流程；
- 已发布内容引用的图片自动进入全员可见的共享媒体库，历史 `/uploads/...` 图片无需迁移；
- CMS 中每个业务字段都有明确的前台消费者、维护用途或兼容理由，不再出现“可以填写但前台永远不显示”的字段。

本次必须重构后台应用壳层、一级导航和各页面工作区。Decap 继续作为内容编辑、Git 存储和发布工作流引擎，但其原生侧栏、集合堆叠方式和媒体入口不再作为最终后台的信息架构。允许复用 Decap 的编辑器和稳定数据能力，不允许仅在现有界面上追加快捷入口、悬浮条、悬浮按钮或弹窗来宣称完成重构。

## 范围与明确不做

### 本次范围

- 审计 `public/admin/config.yml`、Astro schema、数据查询、页面消费者和已有内容，建立字段消费清单；
- 重建后台应用壳层，包括固定主导航、页面标题区、内容工作区、状态反馈和移动端导航；
- 按首页、活动、关于与历史档案、全站设置重新排列 CMS 集合和文件入口；
- 为首页建立显式的公告、活动和荣誉引用关系及顺序；
- 将活动列表置顶与首页展示彻底解耦；
- 清理荣誉正文等无消费者字段，并迁移已有 frontmatter；
- 将图片字段改为支持外部 URL 的自定义图片选择控件，Markdown 继续允许插入图片 URL；
- 新增本地图床配置、通用 HTTP 上传适配器、最近使用图片和共享图片索引；
- 将 Decap 编辑工作流界面收敛为一个“待发布”入口，同时保留一条内容对应一条分支/PR的原生 Git 语义；
- 增加 schema、迁移、单元、构建、CMS 端到端、桌面和移动端验证；
- 同步内容模型、安全、CMS 手册、维护手册和进度文档。

### 明确不做

- 不更换 Astro、Decap CMS、GitHub 后端、OAuth Worker 或 Cloudflare Pages；
- 不实现多条内容组成一个原子发布批次，也不增加预约发布、审核人、退回暂存或后台一键回滚；
- 不迁移、不删除现有 `/uploads/...` 文件；
- 不绑定某一家图床，不首期实现 S3、R2、OSS、COS 等签名协议；
- 不承诺兼容任意私有上传协议，只支持计划中定义的通用 `multipart/form-data` HTTP 适配器；
- 不从后台删除图床原文件，不移动图床目录，不制作完整数字资产管理系统；
- 不做手工多层文件夹、全局重命名、自由关键词或多图床同时启用；
- 不把图床 Token、Secret 或其他凭据写入 Git、内容文件、日志、截图或构建产物；
- 不改变公众前台视觉、不删除历史内容、不改写 Git 历史；后台视觉与结构属于本次重构范围；
- 不在页面底部或角落增加常驻悬浮导航、悬浮操作条、悬浮“图片中心”按钮或覆盖主要内容的 fixed 元素；
- 不并排保留“媒体”和“图片中心”两个入口、两个图库或两套上传逻辑；若 Decap 因配置校验必须保留 `media_folder`，它只能作为不可见的历史兼容项；
- 不以仅修改 collection 标签、增加 hash 链接集合、注入一排快捷按钮或把现有功能包进 dialog 的方式替代真正的页面重组；
- 不发布、不合并 PR、不修改分支保护或外部服务配置，除非用户在实现阶段另行授权。

## 当前事实与相关文件

### 仓库与运行边界

- 正式项目位于 `ccf-scu.github.io/`，生产分支为 `main`，Astro 输出纯静态文件；
- 当前检查时本地 `main` 落后 `origin/main` 2 个提交，实施前必须先重新确认分支和用户改动，不能在未知差异上直接开发；
- CMS 固定为 Decap CMS，后台入口由 `src/admin/main.tsx` 初始化，配置位于 `public/admin/config.yml`；
- 当前 `publish_mode: editorial_workflow`，GitHub 后端会为每一条未发布内容建立独立分支和 PR；本次保留该底层语义；
- 当前媒体配置为 `media_folder: public/uploads`、`public_folder: /uploads`，并存在 `scripts/patch-decap-media-library.mjs` 对 Decap 3.17.1 媒体库空选择缺陷的安装后补丁；替换媒体库后需重新评估并尽可能删除该补丁及 `postinstall` 钩子；

### 已验证的不合理字段和编排

- `homepage.announcementLimit` 位于首页设置，但公告的 `featured` 和 `visible` 位于公告集合；首页实际先按置顶和时间排序再截断，维护动作被拆散；
- 活动同时包含 `featured` 与 `showOnHomepage`。`src/lib/content.ts` 使用前者排序、后者过滤，导致“活动中心置顶”和“首页展示”混为一组内容字段；
- 首页固定展示学术引领、竞赛训练、学业帮扶、生涯发展四个方向；`organization` 活动不得进入首页；
- 荣誉的 `body` 在 CMS 中可编辑，但 `src/content.config.ts` 不声明、`src/pages/index.astro` 和 `src/pages/archive.astro` 也不渲染，属于无效输入；
- 荣誉 `featured` 同时承担首页排序暗示，但维护者无法在首页明确指定三张卡及顺序；
- 成员同时服务关于页本届执委和历史档案，不应复制为两套可编辑数据；`organization.currentCohort` 继续作为本届判断来源；
- 当前首页文案编辑范围保持不变，只重新分组，不将现有可编辑文案硬编码回组件。

## 目标信息架构

Decap 原生侧栏以 collection/file 为单位，无法表达本项目所需的页面级编排。此次不能止步于给原集合加编号或重新排序，必须提供新的后台应用壳层与一级页面路由。原生 collection/file 路由可以作为具体编辑器的内部落点，但维护者日常操作必须从新的页面化导航进入。

新的一级导航固定为：

1. 首页管理；
2. 活动页面；
3. 关于与档案；
4. 全站设置；
5. 待发布；
6. 图片中心。

每个一级导航项必须满足以下结构条件：

- 有独立、可直接访问和刷新的 URL/hash 路由，不依赖先打开别的页面再弹出；
- 有唯一页面标题、用途说明、主要任务和清晰返回路径；
- 页面内容由与该前台页面相关的设置、内容列表和编排模块组成，而不是一组跳往原生集合的无上下文链接；
- 进入具体内容编辑器后仍保留统一后台壳层和当前位置，保存或取消后返回所属页面工作区；
- “待发布”和“图片中心”是与首页、活动同级的正式页面，不是 dialog、抽屉、悬浮按钮或页面底部工具条；
- 桌面端主导航始终占据固定布局区域；移动端改为顶部按钮唤出的模态导航抽屉，关闭后归还焦点，不使用遮挡内容的底部常驻条。

若 Decap 公共扩展 API 无法替换外层导航，实施者必须在技术验证阶段选择并记录一个可维护方案：自定义 React 管理壳层复用 Decap 数据/编辑能力，或对固定版本的 Decap 壳层做受测试的显式适配。不得退回到 `CMS.init()` 后用 `document.body.append(...)`、`MutationObserver` 或零散 DOM 查询注入导航的方案；这种实现即使链接可点击，也视为架构验收失败。

## 后台视觉与交互强约束

### 总体原则

- 后台是独立的管理产品，不复制公众前台的动效或展示型排版；强调稳定、清晰、紧凑和长时间编辑的可读性；
- 视觉层级必须来自应用壳层、页面标题、分区标题、卡片/表格和字段组，不得靠大量悬浮层、阴影或高饱和按钮制造层级；
- 默认使用简体中文；编号仅作为导航辅助，不能用 `01/02/03` 拼接长 collection 名称冒充信息架构；
- 同一种操作在所有页面使用同一名称、位置和视觉等级，例如“保存到待发布”“发布”“取消”“归档”；
- 危险操作与主操作分离；归档、清除本地凭据等动作必须二次确认，且不能紧邻主保存按钮。

### 桌面布局

- 视口宽度不小于 1024px 时，采用左侧主导航 + 右侧主工作区；侧栏建议宽度 232–256px，不得覆盖内容；
- 侧栏顶部显示站点身份和“返回前台”，中部显示六个一级入口，底部仅放账号/退出及必要版本信息；
- 当前一级页面必须有持续可见的选中态，不能只依赖文字颜色；同时使用背景、左侧标记或图标中的至少两项，并满足对比度要求；
- 主工作区顶部为页面标题、简短说明和最多一个主要动作；全局操作不得散落在视口边角；
- 内容容器最大宽度建议 1200–1280px。编辑表单正文列建议 680–800px，辅助说明或预览位于右侧；不得让单行正文输入跨满超宽屏；
- 列表优先使用表格或结构化列表，首页编排使用明确分区和可排序卡片；同一屏不同时出现两套主导航。

### 移动端布局

- 360、390、430px 视口均不得产生页面级横向滚动；
- 主导航收进顶部触发的抽屉或全屏菜单，不能常驻底部遮挡保存按钮、编辑器或系统键盘；
- 页面标题、主要动作和状态信息按自然文档流排列；不使用粘在屏幕四角的长期悬浮按钮；
- 表格在窄屏转为信息卡或受控的局部横向滚动区域，不能压缩成不可读列；
- 编辑预览可在移动端折叠，但字段标签、错误信息、保存和返回必须始终可用；
- 所有点击目标最小 44×44px，抽屉/dialog 关闭后恢复触发元素焦点。

### 视觉令牌

- 优先使用系统中文无衬线字体栈，正文基准 14–16px，页面标题 28–32px，字段标签不小于 14px；
- 采用中性灰白背景、深色正文和单一 CCF 蓝主色；主色只用于当前导航、链接、焦点和主要动作，不把每张卡片都染成蓝色；
- 成功、警告、错误分别使用稳定的语义色，并同时提供文字或图标，不能只靠颜色表达；
- 间距使用 4/8px 基线；常用页面间距限定为 8、12、16、24、32、40px，避免每个模块自行发明数值；
- 控件和卡片圆角限定为 6–12px；阴影仅用于真正浮于页面之上的抽屉、菜单和确认对话框，常规卡片以边框和背景分区；
- 输入、选择、按钮的默认、悬停、聚焦、禁用、错误和加载状态必须完整；焦点轮廓不可移除；
- 正文与背景、按钮文字与按钮背景遵循 WCAG AA 对比度；减少动态偏好下关闭非必要过渡。

### 页面级视觉要求

- **首页管理**：页面内按“页面文案、公告、四个活动位、三项荣誉、开源、招募”形成清晰纵向章节；四个活动槽位必须并列呈现其固定方向和当前所选活动，不能藏在通用字段长表单中；
- **活动页面**：默认显示可搜索、可筛选的活动列表；置顶、时间状态、分类和归档状态在列表中可扫读；“新建活动”是页面唯一主要动作；
- **关于与档案**：以分会信息、本届成员、历届成员、指导老师、相关链接和荣誉记录分区；不得复制两套成员数据入口；
- **全站设置**：联系方式、页脚链接等低频设置分节呈现；本地图床连接不放在这里的普通内容表单里，而从正式“图片中心”页面进入配置区；
- **待发布**：单列展示所有未发布条目，明确类型、标题、修改者、更新时间和逐条发布动作；禁止再显示多列阶段看板；
- **图片中心**：正式全宽页面，也是原“媒体”的唯一替代入口。顶部为页面标题、搜索、来源筛选和“上传图片”，图床连接放入页面内可折叠的设置区或次级路由；图片以响应式网格展示，选中后在详情侧栏显示预览、URL、尺寸/来源、引用位置和复制/选择操作，不以只能关闭才能继续工作的临时 dialog 承载整个功能。
- **图片中心视觉重做**：不得沿用当前灰色大弹窗、两列表单挤在图库上方、等高简陋卡片和右下角悬浮入口。图床配置默认收起，常用的搜索、筛选、上传和选图优先；图片缩略图采用稳定比例、清晰选中态和加载/失败占位，文件名最多两行，元数据弱化，主要操作不在每张卡片上堆成按钮墙。
- **统一媒体语义**：后台文案统一称“图片中心”；不再向维护者显示独立的“媒体”“媒体库”入口。普通图片字段按钮统一为“从图片中心选择”，Markdown 插图、外部 URL、历史图片和图床上传结果均复用同一选择器与索引。

### 明确禁止的补丁式实现

以下任一情况出现即判定后台结构重构不合格，即使自动测试能点击对应按钮：

- 在原 Decap 页面底部增加 fixed 快捷导航条；
- 在右下角增加常驻“图片中心”或“管理台”悬浮按钮；
- 保留原生侧栏不变，仅额外增加一排指向 collection hash 的快捷链接；
- 把图片中心、待发布或页面管理全部实现成覆盖原后台的超大 dialog；
- 依赖 DOM 文本、自动生成 CSS 类名、`document.body.append` 或全局 `MutationObserver` 拼装主要导航；
- 新旧导航并存，导致维护者面对两套入口和两套页面归属；
- 只更改 collection 标签和编号，没有改变维护任务的页面归属、返回路径和编辑上下文；
- 用 CSS 隐藏问题但保留不可访问、可聚焦或屏幕阅读器可读的旧导航。

### 01 首页管理

- `01 首页｜页面内容与展示编排`
  - 保留现有 Hero、分会简介、活动章节文案、成果章节文案、开源章节和招募信息；
  - 首页公告：显式选择 1–10 条公告并拖动排序，不再设置公告数量；
  - 首页活动：固定四个必选槽位，每个槽位选择一个对应类别且未归档的活动；
  - 首页荣誉：固定选择 3 条可见荣誉并拖动排序；
  - 开源入口继续属于首页，而不是普通相关链接。
- `01 首页｜公告内容`
  - 创建和编辑公告本身；
  - 不再包含首页置顶；
  - 保留显示、发布时间、失效时间、链接及确有展示价值的正文。

### 02 活动页面

- `02 活动｜活动内容`
  - 标题、摘要、封面 URL、替代文本、分类、起止时间、正文、来源链接和归档；
  - 新增语义单一的“活动中心置顶”；
  - 删除“首页显示”和“首页优先”；
  - 允许多项同时置顶，置顶组内按开始时间倒序；已结束活动可以置顶；归档始终优先隐藏；

### 03 关于与历史档案

## 目标数据模型与迁移

### 首页显式引用

在 `src/data/homepage.yml` 增加稳定引用，具体字段名在实现时以 schema 审查为准：

```yaml
featuredContent:
  announcements:
    - <announcement-entry-id>
  activities:
    academic: <activity-entry-id>
    competition: <activity-entry-id>
    tutoring: <activity-entry-id>
    career: <activity-entry-id>
  honors:
    - <honor-entry-id>
    - <honor-entry-id>
    - <honor-entry-id>
```

- 引用使用发布后稳定的 entry ID/文件 slug，不使用可能变化的标题；
- 公告允许 1–10 个且不可重复；荣誉必须恰好 3 个且不可重复；四个活动槽位均必填；
- 活动引用必须存在、未归档并匹配槽位类别；`organization` 永远不合法；
- 公告引用必须存在且 `visible: true`；荣誉引用必须存在且 `visible: true`；
- 如果被首页引用的内容后来隐藏、归档、改类或删除，内容校验和构建必须失败并给出可操作错误，不允许静默用其他内容补位；
- 首页按引用顺序渲染，不再根据内容级 `featured` 字段二次排序。

### 活动置顶

- 将活动 `featured` 迁移为语义明确的 `pinned`（最终命名可在实现时统一，但 CMS 标签固定为“活动中心置顶”）；
- 迁移时将现有 `featured: true` 等价转换为 `pinned: true`，保留目前活动列表的置顶意图；
- `src/lib/content.ts` 的活动中心排序为：先排未归档内容，置顶优先，组内按开始时间倒序；
- 首页完全忽略 `pinned`，只使用首页四个显式引用；
- 删除所有活动的 `showOnHomepage`，并从 schema、CMS、校验、测试和文档中移除。

### 公告和荣誉

- 删除公告 `featured`；首页公告由首页引用列表及其顺序决定；
- 删除 `homepage.announcementLimit`；
- 删除荣誉 `featured`；首页荣誉由首页固定三项引用决定；
- 删除荣誉 Markdown 正文及 CMS `body` 字段；迁移前检查现有文件是否含非空正文并生成报告，若存在真实资料不得静默丢弃，需先由负责人决定迁入何处；
- 保留公告可选正文，因为公告可能通过链接或预览使用；实现审计必须再次确认其消费者，若仍无消费者则在迁移报告中单独提出，不擅自删除；
- 成员 `profileConfirmed`、活动 `sourceUrl` 等内部字段在字段消费清单中标注用途。只有确认既无前台消费、又无维护或迁移价值后才能移除。

### 首次迁移的确定性规则

迁移脚本必须可重复运行并先输出 dry-run 报告：

- 首页公告初值使用迁移前生产逻辑所得结果：可见、未失效，先旧 `featured`、再按发布时间倒序，并按旧 `announcementLimit` 截取；
- 四个首页活动初值使用迁移前首页实际展示的四项结果，每个固定方向一项；
- 首页荣誉初值使用迁移前首页实际展示的三项结果，包括既有按标题去重行为；
- 现有活动 `featured` 映射为活动中心 `pinned`；
- 迁移报告列出所有将删除的字段、无法解析的引用、空槽位和非空无效正文；
- 只有 dry-run 结果经人工核对后才写入文件；迁移不得物理删除内容文件或图片。

## 外部图床与共享图片中心设计

### 产品语义

- 图片中心不是图床文件管理器，而是“本站已经使用的图片索引 + 当前浏览器的上传入口”；
- 图片中心同时接管原生“媒体”的浏览、选择和上传职责；维护者不需要理解两套媒体系统；
- 所有人都可浏览、搜索、预览和复用已发布内容引用的图片，无需拥有图床 Token；
- 用户上传新图片或直接粘贴图片 URL 后，该图片立即进入当前浏览器的“最近使用”；
- 内容保存到待发布时，图片随条目暂存，但不会提前污染全员共享索引；
- 条目正式发布并完成静态构建后，图片从已发布内容中被自动收集，进入全员共享媒体库；
- 相同 URL 精确去重；同一图片可记录多个使用位置和多个替代文本；
- 图片不再被任何已发布内容引用时标记为未使用或从默认结果中隐藏，不删除图床原文件；
- 直接粘贴 URL、图床上传所得 URL、Markdown 图片和历史 `/uploads/...` 路径遵循同一收集规则。

### 图片索引

构建期生成不含秘密的静态索引，例如 `media-index.json`。实现时应从以下已发布来源提取：

- 活动封面；
- 成员、指导老师照片；
- 荣誉图片；
- 首页、全站或 SEO 设置中的图片字段；
- Markdown 标准图片语法中的 URL；
-仍被内容引用的 `/uploads/...` 历史资源。

每个索引项至少包含：

- 原始 URL；
- 推断出的文件名；
- 来源类别（活动、成员、老师、荣誉、正文、全站或历史）；
- 引用内容的稳定 ID、标题和后台编辑入口；
- 可取得的替代文本；
- 首次发现信息若无法在无状态构建中可靠保存，则不伪造时间，可改为当前内容的发布时间或省略；
- 是否为站内历史资源；
- 当前引用数量。

索引生成必须解析标准 Markdown 图片节点，而不是用易误判代码块和转义文本的简单正则。索引是可再生构建产物，不作为新的内容真源，不为每次上传额外创建 PR。

### 本地图床配置

首期只支持一个当前启用的通用 HTTP 图床配置：

- 图床显示名称；
- `multipart/form-data` 上传接口 URL；
- 文件字段名，默认 `file`；
-认证 Header 名称及 Token/值；
- 可选的固定表单字段；
- 从 JSON 响应读取最终图片 URL 的字段路径，例如 `data.url`；
- 测试配置/测试上传；
- 清除本地配置和凭据。

非敏感配置可保存在 `localStorage`。Token 默认只进入 `sessionStorage`；用户主动勾选“在本机记住凭据”后才可进入 `localStorage`，界面必须明确提示仅在私人、受信设备使用。字段不得进入 Redux 调试输出、URL、Git、日志、错误详情或截图。

“用户自行定义图床”表示可配置上述通用协议参数，不表示执行任意 JavaScript、任意请求模板或绕过浏览器 CORS。目标图床必须允许 `/admin/` 所在来源发起跨域上传。配置测试需区分：CORS 拒绝、网络错误、HTTP 错误、JSON 解析失败、响应路径错误和成功但 URL 非法。

### CMS 控件

- 注册统一的外部图片控件和媒体库集成；普通图片字段通过“从图片中心选择”进入同一选择器，可选择共享图片、上传新图或粘贴 URL；
- Markdown 保留原生编辑能力，并提供插入共享图片 URL/上传后插入的入口；若 Decap 原生 Markdown 工具栏无法无补丁扩展，则保留标准 Markdown 粘贴方式并在图片中心提供“一键复制 Markdown”；
- 图片字段不再调用仓库媒体上传；维护者可见的原生“媒体”入口必须移除或由图片中心正式替换。一级图片中心和字段内选择器复用同一数据层；选择器可使用受控 dialog，但完整图库与图床设置只能存在于正式页面；
- 最近使用列表只保存在当前浏览器，可包含尚未被内容引用的上传结果，并提供清空功能；
- 全员共享列表首期支持按来源分类、标题/文件名/URL 搜索、预览、复制 URL、查看引用位置；
- 不提供删除图床原文件、远程重命名、远程移动或多层手工分类。

### URL 与内容安全

用户确认“不做图床域名白名单或归属校验”，因此不限制到指定图片域名。但仍必须保留最低协议和输出安全边界：

- 允许现有站内绝对路径和外部 `https://` 图片；生产 HTTPS 页面不得新增会被浏览器拦截的 `http://` 混合内容；
- 拒绝 `javascript:`、`data:text/html`、`file:` 等可执行或本地协议；是否允许受控 `data:image/*` 应在实现前安全评估，默认不允许持久化；
- 上传前在浏览器检查文件大小、声明 MIME 和可解码性；限制值在实施时写入配置、文档和测试；
- 外部图床可能失效、限流、替换内容或追踪访客，维护手册必须说明版权、隐私、稳定性和防盗链责任；
- 前台不加载图床上传 SDK、Token 或 CMS bundle，只加载最终图片 URL。

## 验收标准

### 信息架构和字段

- 后台显示唯一的新应用壳层和六个一级页面；原生 collection 侧栏不再作为维护者主导航；
- 六个一级入口均有可刷新、可直达的路由，图片中心和待发布不是悬浮层；
- 后台入口按目标页面组织，维护者能从页面标题、当前位置和说明判断改动影响哪个前台页面；
- 首页同一设置入口可完成公告顺序、四个活动槽位和三项荣誉的编排；
- 四个活动槽位全部必填、类别正确且不接受 `organization`；
- 活动编辑页不再出现“首页显示”或“首页优先”，只保留“活动中心置顶”；
- 多个活动可同时置顶，置顶组内按开始时间倒序；已结束活动可置顶；归档内容不显示；
- 荣誉编辑页没有正文和首页精选；公告没有首页置顶；首页没有公告数量；
- 每个 CMS 字段均在字段消费清单中有前台消费者或明确维护理由。

### 视觉、布局和可访问性

- 1024px 以上采用不遮挡内容的左侧主导航和右侧工作区；360/390/430px 使用可关闭且恢复焦点的移动导航；
- 页面底部和角落不存在常驻 fixed 快捷条或悬浮业务入口；保存按钮、编辑器和系统键盘不被覆盖；
- 当前页面、主要动作、次要动作、危险动作和状态反馈具有一致且可辨认的视觉层级；
- 首页四个活动槽位、三项荣誉和公告编排拥有专用结构，不被埋在无分组的长表单里；
- 活动列表、待发布列表和图片网格在桌面与移动端均可扫读、可键盘操作且没有页面级横向溢出；
- 键盘可遍历六个一级入口、列表操作、编辑表单、图床配置和图片选择；焦点可见，dialog/抽屉焦点行为正确；
- 正文和交互控件达到 WCAG AA 基础对比度，状态不只依赖颜色，减少动态偏好得到遵守；
- 截图证据必须包含六个一级页面中的代表页面、具体编辑器、桌面侧栏、移动端导航和图片中心，不接受只截原 Decap 页面加附加条作为验收。

### 工作流

- 新建或编辑内容后可以保存到唯一的“待发布”入口，正式站内容不变化；
- 待发布列表不要求维护者在草稿、审核中、待审核等状态间移动；
- 任一有写权限的维护者可逐条发布；发布一条不会连带发布其他条目；
- 后台不提供预约发布、退回暂存、取消发布或批次发布；
- 发布后的 Git 分支/PR 清理、构建触发和失败反馈保持可追踪；
- Git 历史仍可用于仓库级回滚，但后台不增加回滚按钮。

### 图片中心

- 后台只出现一个“图片中心”入口，原生“媒体”入口不可见、不可聚焦且不被屏幕阅读器重复读取；
- 未配置图床时仍可浏览共享图片、选择历史图片和直接粘贴 URL；
- 普通图片字段和 Markdown 使用图片中心的统一选择器，选择完成后保留编辑器上下文和未保存内容；
- 配置兼容的 HTTP 图床后可测试连接、上传图片并自动取得 URL；
- 上传成功后图片进入本机最近使用，并能直接填入普通图片字段；
- 直接粘贴的 URL 同样进入本机最近使用；
- 待发布内容引用的图片不会提前出现在其他用户的共享库；正式发布并重新构建后会出现；
- 活动、成员、老师、荣誉和 Markdown 中的已发布图片均能被索引；
- 相同 URL 不生成重复卡片，引用位置能够聚合展示；
- 其他维护者无需图床 Token即可查看、复制和选择共享图片；
- Token 不出现在仓库 diff、构建产物、URL、错误日志或测试截图；
- 清除本地配置后上传能力关闭，但已发布图片仍可浏览和复用；
- 图床 CORS 拒绝、超时、错误响应、错误 JSON 路径和无效 URL 均有中文可操作提示；
- 后台没有删除图床原文件的入口。

### 兼容性和质量

- 所有现有 `/uploads/...` 图片继续显示，不进行迁移；
- 已有 34 个静态页面及前后台 bundle 隔离不回归；
- 内容 schema、CMS 配置、迁移脚本和页面查询使用一致字段；
- 首页、活动列表、活动详情、关于、档案、搜索和后台在桌面及至少 390px 移动视口通过验证；
- JavaScript 或图床上传失败不影响已发布前台内容；
- 根路径和 `SITE_BASE=/preview-site/` 子路径构建均通过。

## 分阶段步骤

1. **建立基线与字段消费矩阵**
   - 更新本地分支前先确认用户授权和工作树状态；读取最新生产提交；
   - 列出每个 CMS 字段、schema、数据文件、查询和页面消费者；
   - 对现有首页实际选择结果、无效正文和旧字段值生成只读报告；
   - 补充当前行为回归测试，作为迁移前基线。

2. **技术验证：Decap 扩展边界**
   - 在固定版本上制作最小原型，验证自定义后台壳层、一级路由、编辑器嵌入/衔接、自定义媒体库、图片控件、Markdown 插入和单一待发布入口；
   - 原型必须先证明原生主导航可以被真正替代，保存/取消可回到所属页面，刷新深层链接不丢失上下文；
   - 验证 Decap 是否要求保留占位 `media_folder`，以及旧媒体补丁能否移除；
   - 验证 GitHub editorial workflow 中从单一列表直接逐条发布的安全路径；
   - 验证主流兼容图床的 CORS、multipart 上传和响应 URL 提取；
   - 若任何关键扩展必须依赖未公开内部 API，在计划“发现与证据”中记录固定版本、守卫和替代方案后再进入正式实现。

3. **schema 先行与确定性迁移**
   - 先实现新 schema、引用校验和 dry-run 迁移器；
   - 生成并人工核对首页公告、活动、荣誉初始引用；
   - 迁移活动置顶并清除废弃字段；
   - 对非空荣誉正文停止自动写入并请求内容负责人决定，不能静默丢失；
   - 同步示例、测试夹具和兼容读取策略。

4. **前台查询改为显式首页编排**
   - 首页严格按 `homepage.yml` 引用和顺序渲染；
   - 活动中心独立使用 `pinned` 排序；
   - 删除旧的自动首页候选、公告截断和荣誉精选逻辑；
   - 保持现有前台布局、动画和响应式视觉不变。

5. **重建后台应用壳层、信息架构和字段**
   - 实现唯一的桌面侧栏、移动导航、页面标题区、六个一级路由和统一返回行为；

## 决策记录

- 首页使用显式引用，不再依据分散在内容条目上的首页布尔开关自动推断；维护者所见即所得，错误引用由构建阻断。
- 首页固定四个活动方向且每项必选；组织建设活动只属于活动中心。

- 成员只维护一份，关于页和历史档案按 `currentCohort` 分流。
- 保留 Decap 每条内容独立发布，不实现批次；只简化维护者可见的工作流入口。
- 图床不绑定服务商，首期只支持可配置 multipart HTTP 上传；复杂云签名协议延期。

- 不设图床域名白名单，但仍保留安全协议限制、混合内容防护和上传文件基础校验。
- 不迁移或删除历史图片；新旧图片在共享索引中统一展示。
- 后台视觉必须随信息架构一起重构；公众前台视觉保持不变。
- Decap 只保留为内容和 Git 工作流引擎，原生外壳不是不可改变的产品界面。
- 主要导航必须由受控的应用结构和路由实现；`document.body.append`、全局 `MutationObserver`、fixed 快捷条和悬浮按钮不得承担主信息架构。

## 风险与回滚

- **Decap 内部 API 风险**：单一待发布界面和媒体库可能触及版本相关扩展点。使用公开注册 API优先；不得避免版本守卫；升级 Decap 前必须跑 CMS E2E。
- **图床兼容风险**：不同服务的字段、认证、CORS 和响应格式差异大。以受限通用协议、测试连接和清晰错误为边界，不宣称全兼容。
- **凭据风险**：长期浏览器存储可能被同源脚本或失陷设备读取。默认只存会话，长期记住必须主动选择并提示风险；推荐受限、可撤销上传 Token。
- **外部图片风险**：防盗链、失效、内容替换、性能和隐私不受本站完全控制。保留 URL 审计和引用列表，文档要求选择稳定 HTTPS 图床。
- **引用完整性风险**：显式首页引用可能在内容归档或改类后失效。schema/构建硬失败优于静默替换，并提供具体修复路径。
- **迁移风险**：删除旧字段可能改变当前首页或活动列表。迁移以生产算法生成初值、dry-run 对照和可重复脚本控制。
- **并发风险**：首页设置仍是单个 YAML 文件，多人同时编辑可能产生 Git 冲突。待发布界面必须显示冲突；维护手册建议同一时间只由一人编排首页。
- **共享索引时效**：图片只有在内容发布并重新构建后才对其他人可见，这是已确认产品语义；构建失败时不得假称已经共享。

回滚以本任务自包含 commit 为单位执行 `git revert`，不使用 reset 或改写历史。迁移脚本在写入前生成报告；旧字段兼容读取至少保留一个受控迁移窗口，待新内容、构建和生产验证通过后再删除。现有 `/uploads/...` 资源始终保留，因此回滚无需恢复图片文件。
